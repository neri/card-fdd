# SD リーダーモード 計画書

Cardputer に挿した MicroSD カード全体を、USB マスストレージ（普通のリムーバブルディスク）として PC に見せるモードを追加する。
フロッピーイメージを PC から SD に置くとき、SD を抜き差ししなくて済むようにするのが目的（PLAN.md 1 章の「将来の課題」、Q6）。
現行の要件・設計は [PLAN.md](PLAN.md) と [DESIGN.md](DESIGN.md) を前提とし、この文書はリーダーモードで変わる部分だけを扱う。

- ステータス（2026-11-26）: R1〜R5c と R4（文書）を終えた。Linux での読み書き、切り替え・終了、速度の改善（読み出し 1.1 倍、書き込み 2.5 倍）を実機で確認した（11 章、13 章、14 章）。Windows と、v1.1・Adv の両機種でも動作を確認した（2026-11-26）。残りは任意の R5d と、11 章の未確認の項目（使用中のカードの抜き取り、挿入中・転送中に入ること）
- 対象: Cardputer v1.1 と Cardputer-Adv（[ADV_PLAN.md](ADV_PLAN.md)）。機種による違いはない
- **方針: リーダーモードは SD のメンテナンス用なので、速さより「簡単で確実に動く」ことを優先する。** 機能は「PC から SD を読み書きできる」「安全に通常モードへ戻れる」の 2 つに絞る
- 実機で使ってみると、FAT32 のカードをマウントするまでが思ったより遅かった。そのため、動くものができた後の R5 で速度を改善する。R5 でも「簡単で確実」の方針は変えず、仕組みの大きな変更（DMA による先読み、書き込みのキャッシュなど）はしない（14 章）

## 1. 概要

| 項目 | 通常モード（今） | リーダーモード |

| 入り方 / 出方 | — | 本体のキーで再起動して切り替える（2 章） |

## 2. モードの切り替え

### 2.1 再起動で切り替える理由

USB のディスクリプタ（インターフェースのサブクラス・プロトコル、CBI の割り込みエンドポイント、VID / PID）は `usb::build` で起動時に一度だけ組み立て、`StaticCell` に置いている（`src/usb/mod.rs`、`src/bin/main.rs`）。
embassy-usb には、動いている途中でディスクリプタを組み直す仕組みがない。そのため、**フラグを残して再起動し、起動時にモードを選ぶ**。再起動の処理（`board::system::reboot`）は、USB を切り離してホストに「抜けた」と見せるところまで既にできている。

### 2.2 操作（案）

| 操作 | 動作 |
|------|------|
| 通常モードで `Ctrl+Alt+S` | フラグを立てて再起動 → リーダーモード。転送中なら終わってから。PC がフロッピーの取り外しを禁止している（PREVENT ALLOW MEDIUM REMOVAL）ときは警告し、3 秒以内にもう一度押すと進む。空イメージの作成中は受け付けない |
| リーダーモードで `Esc` | 終了の確認（6 章）→ 再起動 → 通常モード |
| リーダーモードで `Ctrl+Alt+R` / `Ctrl+Alt+D` | 今と同じ（再起動 / ダウンロードモード） |

`Ctrl+Alt+S` は今は何も割り当てられていない（`App::on_key`）。リーダーモードでは、ほかのキーは受け付けない。

- キーマトリクスにダイオードがないため、Ctrl・Alt・S を同時に押すと、マトリクスの長方形の 4 つ目の角にあたる Shift も押されたように読める（v1.1 では Ctrl = アドレス 4・入力 0、Alt = 4・1、S = 1・1 で、幽霊が 1・0 = Shift。Adv も物理的な配線は同じ）。そのため文字は `'S'` になる。`'s'` と `'S'` の両方を受け付ける（実機で `'s'` だけでは反応しなかった。2026-11-25）
- `Esc` は Fn+`` ` `` で入力する。`` ` `` 単体（セレクターの「上の階層へ」と同じキー）でも終了できるようにした

挿入中のイメージは取り出さずにそのまま再起動する。フロッピーへの書き込みは SD に直接書いていて、挿入しても FAT は変わらないので、先に書き出すものがない。設定ファイルの `last_image` も消さないので、通常モードに戻ると前のイメージが自動で挿入される（`auto_mount` が有効なとき）。

`dev-cdc` ビルドでは、CDC-ACM のコマンド `reader`（通常モード。`Ctrl+Alt+S` と同じ）と `exit`（リーダーモード。`Esc` と同じ）でも切り替えられる。

### 2.3 フラグの置き場所（案）

**`LPWR` の `STORE0` レジスタ**に、マジックナンバー（`0x53445244`、"SDRD"）を書く（`board::system`）。ソフトウェアリセットでは消えず、電源を切ると消える。

- 起動時に読んだらすぐ消す（「1 回だけ」のフラグ）。だから通常モードに戻るときは、ただ再起動すればよい。リーダーモードの途中でクラッシュしても、電源を入れ直しても、必ず通常モードで起動する
- 設定ファイルには置かない（リーダーモード中は SD の FAT に触らないので、出るときに消せない）
- `STORE` レジスタは、今のダウンロードモードへの再起動（`LPWR` の `option1`）と同じくレジスタを直接書くだけで済む。RTC FAST メモリの変数（`#[ram(unstable(rtc_fast, persistent))]`）も候補だったが、リンカーやブートローダーの扱いを確かめる手間が増えるので採らなかった
- `STORE0` を選んだ理由: esp-hal 1.2.2 のソースで使っているのは `STORE1`〜`STORE5`（クロックの校正値、起動時刻、XTAL の周波数など）で、`STORE0` は使っていない。ESP-IDF では `STORE6`（スリープ復帰の入口）と `STORE7`（RTC メモリの CRC）も使い、`STORE0` は「予約」とされている。万一ほかの何かが書き換えても、マジックナンバーと一致しなければ通常モードで起動するだけで済む（実機で確かめる。13 章）

## 3. 起動の流れ

`src/bin/main.rs` で、SD の SPI の初期化の後に分岐する。液晶、キーボード、音、LED、電池の初期化は両モードで共通。

```
液晶・LED・電池・機種判別・キーボード・音・SD の SPI
        │
        ├─ フラグなし ──→ 今と同じ（mount_card → USB(設定のモード) → auto_insert → メインループ）
        │
        └─ フラグあり ──→ カードの容量を読む（ここでカードが初期化される）
                          → USB(SCSI+BOT、リーダー用の固定 ID)
                          → リーダー用のメインループ
```

- リーダーモードでは `mount_card` を呼ばない。ボリュームもファイルも一度も開かないので、閉じ忘れや、PC の書き込みと本体のキャッシュの食い違いが起きようがない
- 設定ファイルも読まない（読む必要のある項目がない）
- 自動挿入（`auto_insert`）も設定の保存（`save_config`）もしない
- 容量が読めない（カードがない、壊れている）ときは、エラーを表示する。`Esc` ですぐ通常モードに戻れる。USB は起動する（PC からは媒体のないドライブに見える）。起動しない分岐を作るより、コードの道筋が 1 本で済むため（計画からの変更）

## 4. USB の識別情報

| 項目 | 値（案） | 理由 |
|------|---------|------|
| 方式 | SCSI+BOT（サブクラス 0x06、プロトコル 0x50） | どの OS でも標準のドライバで普通のディスクとして見える |
| VID / PID | **`1209:0002`**。pid.codes のテスト用 PID（`0x0001`〜`0x0010`）の 1 つで、今の既定（`1209:0001`）とは別の値。社内のテストでは誰でも使えるが、配布・販売する機器には使えない（README の既知の問題に書いてある `1209:0001` と同じ扱い） | 通常モードを TEAC の ID（`usbstor.inf` でフロッピー用ドライバが割り当たる）にしていると、同じ ID ではリーダーとして使えない。Windows は VID / PID / シリアルごとにデバイスの情報を覚えるので、モードごとに分ける |
| シリアル | `CARDSD0001` | 同上 |
| 製品名（ディスクリプタ） | `SD Reader` | |
| INQUIRY | ベンダー `CARDFDD `、製品 `SD Reader       ` | |

どれもコードに固定で書き、設定ファイルでは変えない。`dev-cdc` ビルドでは、今と同じく CDC-ACM と組み合わせた複合デバイスにする。

## 5. 本体からの SD アクセスの排他

PC はカード上の FAT を自分の都合で書き換える。本体が同時に FAT を読み書きすると、どちらの見え方も壊れる。

- リーダーモード中、SD に触るのは USB のブロック読み書きだけにする。`Browser` のファイルシステムの機能（一覧、設定ファイル、空イメージ）は使わない
- 実装では、リーダーモード用のメインループと画面（7 章）を `App` とは別に作り、`App` は作らない。`App` に「リーダー中」のフラグを足して各所で分岐するより、うっかり SD を触る経路が残りにくい

## 6. 終了と安全な取り外し

- PC からの取り出し（START STOP UNIT の LoEj）を受けたら、以降は媒体なし（NOT READY / MEDIUM NOT PRESENT）を返し、画面に「取り外して大丈夫」と出す（今の `HOST.take_eject_request` を使う）
- 本体の `Esc` での終了:

| 状態 | 1 回目 | 2 回目（3 秒以内） |
|------|--------|------------------|
| PC が取り出し済み / カードのエラー / USB 未接続 | すぐ再起動して通常モード | — |
| 取り出し前 | 「PC で取り出してください」と警告 | 強制的に再起動 |

- 今の `e` キー（2 回押しで強制取り出し、`FORCE_EJECT_WINDOW`）と同じ操作感にする
- 転送中（`HOST.is_busy()`）は、強制でも転送が終わってから再起動する
- Linux の `umount` だけでは START STOP UNIT が来ないので、取り出しが来たことは「安全」の目安にとどめる。文書に「PC 側で取り出してから終了する」と書く

## 9. 実装

### 9.1 `Disk` トレイトの一般化

今の `Disk` トレイトは容量をフロッピーのジオメトリ（`Geometry`、CHS）で返していて、USB 側（READ CAPACITY、範囲の確認、ブロック長）もそれを使っている。
カード全体は CHS で表せないので、容量を別に返せるようにする。

```rust
/// Size of the medium in blocks.
pub struct Capacity { pub blocks: u32, pub block_size: u16 }

pub trait Disk {
    fn geometry(&self) -> Option<Geometry>;
    /// Defaults to the geometry's size. Disks without a CHS geometry override this.
    fn capacity(&self) -> Option<Capacity> {
        self.geometry().map(|g| Capacity { blocks: g.total_sectors(), block_size: g.bytes_per_sector })
    }
    // ...
}
```

- 既定の実装がジオメトリから計算するので、`ImageDisk` と `RamDisk` は変えなくてよい
- `command.rs` の READ CAPACITY、READ / WRITE の範囲確認（`rw`）、READ FORMAT CAPACITIES と、`transfer::block_size` を `capacity()` に切り替える
- フロッピー専用の処理（MODE SENSE のフレキシブルディスクのページ、FORMAT UNIT、シーク音と実機速度の `mechanics`）は `geometry()` のまま。リーダーでは `geometry()` が `None` なので、`mechanics` は既に何もしない
- 媒体がないときの READ FORMAT CAPACITIES は、今はフロッピーの最大容量（`DRIVE_MAX`）を返している。SCSI モードでの扱いを見直す
- SD の容量は SDXC の上限 2TB までなので、READ CAPACITY(10)（32 ビットの LBA）で足りる。READ(16) / READ CAPACITY(16) は実装しない

### 9.2 `ReaderDisk`（新規、`src/storage/reader.rs`）

- `Disk` を実装する。`capacity()` はカードの容量（embedded-sdmmc の `SdCard::num_bytes()` / 512）、`geometry()` は `None`、`write_protected()` は常に `false`
- カード（embedded-sdmmc の `BlockDevice`）を直接持ち、読み書きする。LBA の変換はせず、カードの物理ブロックをそのまま渡す。リーダーモードでは `Browser` を作らないので、ファイルシステムの機能をうっかり使う経路がそもそもない
- 状態は「使える / 取り出し済み / エラー」の 3 つだけ。取り出し済みとエラーのときは `capacity()` が `None` を返す（USB 側は今の仕組みで媒体なしを返す）

## 14. 速度の改善（R5）

### 14.1 分かっていること

- 実測（リーダーモード、Linux、2026-11-25）: 書き込み約 115KB/s（5.9MB を書いて `sync` まで 52 秒）、読み出し約 260KB/s（再マウント後に 5.9MB を読んで 23 秒）
- 読み出しは 1 ブロック（512 バイト）あたり約 2ms かかっている。SPI 20MHz で 512 バイトを送るだけなら約 0.2ms なので、残りは 1 ブロックごとのコマンド（CMD17 / CMD24）とカードの応答待ち、USB の 64 バイトパケット 8 個の送受信にかかっていると考えられる。今は「SD から 1 ブロック読む → USB で送る」を順番に繰り返していて、両者は重ならない（`usb::transfer` の `DataPhase::Read` / `Write`）
- 内訳は R5a で測った（14.6 節）

### 14.2 FAT32 のマウントが遅い理由（見込み）

- FAT32 では、空き容量を出すために OS が FAT 全体を読むことがある。Linux は FSInfo セクタの空きクラスタ数が無効なときに、Windows はマウント時に、FAT 全体を読むと言われている（Windows は未確認）
- 7.5GB のカードをクラスタ 4KB で FAT32 にすると、FAT は約 7.5MB（4 バイト × 約 190 万クラスタ）になる
- **R5a で確かめた（Linux）**: カードはクラスタ 4KB・1,957,642 クラスタで、FAT は約 15,300 ブロック（7.8MB）。自動マウントで 3,575 ブロック、続く `df` で 5,471 ブロックを読み、`df` に 5.4 秒かかった。再マウントのたびにファイルのデータとは別に約 8,600 ブロックを読んでいる。FAT 全体の走査が遅さの主な原因と見てよい
- だとすると、効く手は 2 つある
  1. 読み出しを速くする（R5 の本題）
  2. カードをクラスタの大きい FAT32（32KB など）でフォーマットする。FAT が 8 分の 1 になる。コードの変更は要らないので、文書に「おすすめ」として書く
- まず R5a で、マウントのときに何ブロック読まれているかを数えて、この見込みが正しいか確かめる

### 14.3 進め方

「簡単で確実」の方針どおり、効果が大きく、仕組みを大きく変えないものから順に入れる。1 段ごとに実機で測り、ハッシュの照合（11.1 節と同じ手順）を繰り返す。

| 段 | 内容 | 期待 |
|----|------|------|
| **R5a. 測る**（完了） | 1 コマンドあたりの SD の時間と USB の時間を `UsbStats` に足し、`dev-cdc` の `stats` で見られるようにする。マウント中に読まれたブロック数も数える。PC 側では、再マウント後のファイルの読み出し時間、`udisksctl mount` と `df` の時間を測る | どこに時間がかかっているかが分かる |
| **R5b. マルチブロック読み出し**（完了） | 1 コマンドの連続したブロックを、最大 8 ブロック（4KB）ずつ SD のマルチブロック読み出し（CMD18）でまとめて読み、まとめて USB で送る | 1 ブロックごとのコマンドと応答待ちが 8 分の 1 になる |
| **R5c. マルチブロック書き込み**（完了） | USB から最大 8 ブロックを受け取ってから、マルチブロック書き込み（CMD25）でまとめて書く。コマンドをまたいで溜めない（書き込みは今と同じく、コマンドの完了を返す前に SD に届く） | 書き込みも同じく速くなる |
| R5d. SPI クロック（任意） | 20MHz → 25MHz（SPI モードの上限）。カードとの相性を見て、だめなら戻す | 数 % 程度 |

やらないこと: SPI の DMA と USB の送受信を重ねる先読み、コマンドをまたぐ書き込みキャッシュ、USB High Speed（ESP32-S3 は Full Speed だけ）。Full Speed の実効は 1MB/s 前後なので、R5b / R5c で数百 KB/s 台まで上がれば十分とする。

### 14.3.1 R5a の計測方法

- `usb::transfer` の READ / WRITE のデータフェーズで、1 ブロックごとに SD の時間（`Disk::read` / `write`）と USB の時間（パケットの送受信）を µs 単位で足し込む（`usb::perf::PERF`）。フロッピーの実機速度モードの待ち（`mechanics`）は含めない
- `dev-cdc` ビルドの CDC コマンド `perf` でログに出し、`perf reset` で 0 に戻す。通常モードとリーダーモードの両方で使える
- 出力: リセットからの経過時間とデータフェーズの合計時間、方向ごとのコマンド数・ブロック数・1 コマンドの最大ブロック数・SD と USB の時間（合計と 1 ブロックあたり）・データフェーズだけで見た速度
- 手順: `perf reset` → PC でマウント → `perf`（マウントで読まれたブロック数）→ `df` → `perf` → ファイルの書き込みと `sync` → `perf` → 再マウントして読み出し → `perf`

### 14.4 実装の方針

- `Disk` トレイトに複数ブロックの読み書き（`read_blocks` / `write_blocks`）を足す。既定の実装は今の `read` / `write` を繰り返すだけにし、`ImageDisk` と `RamDisk` はまず変えない
- `ReaderDisk` は、embedded-sdmmc の `BlockDevice::read` / `write` に複数の `Block` を渡す（CMD18 / CMD25 になる）
- `usb::transfer` の `DataPipe` のバッファを 1 セクタ分から 8 ブロック分（4KB + パラメータ）にする。`DataPipe` は `MassStorage` の中にあり、今は `usb::build` の戻り値として一度スタックを通る。4KB 増えるとスタックが足りなくなるおそれがあるので、バッファを `static` に置くか、`StaticCell` の中で直接作るようにする
- フロッピーの `ImageDisk` も、イメージの連続範囲（`fat::Extent`）の中なら同じ方法で速くできる（PLAN.md の Phase 8 の「書き込みの高速化」）。リーダーモードで効果を確かめてから、別の段で入れる
- エラーのとき: まとめて読み書きした範囲のどこかで失敗したら、その範囲全体を失敗として扱う（今と同じく MEDIUM ERROR を返し、`ReaderDisk` はエラー状態になる）

### 14.5 完了条件

- データフェーズの速度（`perf`）が、14.6 節の実測より速くなる。目安は R5a の結果から決め直した: 書き込みは 2 倍以上（120KB/s → 240KB/s 以上）、読み出しは 1.3 倍以上（431KB/s → 560KB/s 以上）
- 読み出しは R5b の結果（14.7 節）から、SD と USB を重ねない方針のままでは 1.3 倍に届かないと分かった。読み出しの目安は「R5b の 473KB/s を下回らない」に下げる
- FAT32 のカードのマウントにかかる時間が短くなる（R5a で測った時間と比べる）
- 11.1 節のハッシュの照合が通る。フロッピーモードの読み書き（Windows の A: と Linux）も今までどおり動く

### 14.6 R5a の結果（2026-11-25、Linux、`dev-cdc` ビルド、カード 7.5GB・FAT32・クラスタ 4KB）

| 操作 | PC 側の時間 | 読み書きしたブロック | SD（1 ブロックあたり） | USB（1 ブロックあたり） | データフェーズの速度 |
|------|------------|---------------------|----------------------|------------------------|--------------------|
| リーダーモードに入ってから自動マウントまで | 約 6.2 秒（USB の認識まで 1.0 秒） | 読み 3,575 | 571µs | 591µs | 430KB/s |
| `df`（空き容量） | 5.4 秒 | 読み 5,471 | 567µs | 592µs | 431KB/s |
| 5.9MB の書き込み + `sync` | 53.6 秒 | 書き 11,951 | **3,242µs** | 919µs | 120KB/s |
| 再マウント後に 5.9MB を読んで照合（42/42 一致） | 22.3 秒 | 読み 20,605 | 568µs | 589µs | 431KB/s |
| 参考: フロッピーモード（Linux の自動マウント） | — | 読み 179 | 611µs | 850µs | 342KB/s |

分かったこと:

- どの操作でも、経過時間のほとんど（読み出しで約 98%、書き込みで約 91%）がデータフェーズ。PC は本体を待っている
- **書き込みは SD が律速**。1 ブロックごとの書き込み（CMD24）でカードの書き込み完了待ちが毎回入り、1 ブロック 3.2ms かかる。マルチブロック書き込み（R5c）の効果がいちばん大きいはず
- **読み出しは SD と USB が半々**。SD は 1 ブロック 568µs（SPI で 512 バイト送るだけなら約 205µs）で、マルチブロック読み出し（R5b）で 250〜300µs 程度まで縮む見込み。USB は 1 ブロック（64 バイトのパケット 8 個）で 590µs、1 パケット 74µs。Full Speed の上限（1 パケット約 53µs）に近いので、USB 側はあまり縮まない。SD と USB を重ねない方針のままだと、読み出しは 1.3〜1.4 倍（560〜600KB/s）が上限の見込み
- 前に測った「読み出し約 260KB/s」は、ファイルの読み出し時間から出した値で、再マウント後の FAT の走査（約 8,600 ブロック）を含んでいた。データフェーズそのものは約 430KB/s
- FAT の走査（約 15,300 ブロック）は、読み出しを 600KB/s にしても 13 秒前後かかる。クラスタを 32KB にすると FAT は約 1,900 ブロックになり、今の速度でも 2 秒ほどで済む。**カードはクラスタの大きい FAT32 でフォーマットするのがいちばん効く**（文書に書く）
- 書き込み直後の最初の起動だけ、フロッピーモードの SD が 1 ブロック 5.5ms と遅かった（再起動後は 611µs）。原因は調べていない

### 14.7 R5b の結果（2026-11-25）

実装: `Disk` に `max_read_blocks()` と `read_blocks()` を追加した（既定は 1 ブロックずつで、フロッピーは今までどおり）。`ReaderDisk` は最大 8 ブロックを 1 回のマルチブロック読み出し（CMD18）で読む。`usb::transfer` のバッファは 4KB + 64 バイトにし、`ConstStaticCell` で静的に置いた（スタックを通らない）。

| 設定 | 操作 | 読んだブロック | SD / ブロック | USB / ブロック | データフェーズの速度 |
|------|------|--------------|--------------|---------------|--------------------|
| R5a（1 ブロックずつ） | 再マウント後の読み出し | 20,605 | 568µs | 589µs | 431KB/s |
| **R5b（8 ブロックずつ）** | 再マウント後の読み出し（42/42 一致） | 20,605 | 387µs | 668µs | **473KB/s** |
| R5b（8 ブロックずつ） | `df`（FAT 全体、15,575 ブロック、15.0 秒） | 15,575 | 387µs | 668µs | 473KB/s |
| 試しに 32 ブロックずつ | `df`（14.1 秒） | 15,055 | 365µs | 679µs | 478KB/s |
| R5b | フロッピーモード（Linux の自動マウント） | 179 | 611µs | 897µs | 331KB/s |

分かったこと:

- SD は 1 ブロック 568µs → 387µs に縮んだが、USB が 589µs → 668µs に増え、合計では 1.1 倍（431 → 473KB/s）にとどまった
- USB が増えたのは、計り方の差と考えられる。embassy-usb の Synopsys ドライバの `write` は 64 バイトのパケット 1 個しか受け付けず、前のパケットをホストが受け取るまで待つ。1 ブロックずつのときは、最後のパケットがホストに届くのを待つ時間が次の SD の読み出しと重なり、USB の時間が小さく見えていた。実際の USB の時間は 1 パケット約 84µs（ホストがパケットを取りに来る間隔）で、1 ブロック約 670µs
- 32 ブロックずつにしても USB は変わらず、SD が少し縮むだけ（+1%）。RAM を 24KB 余分に使うほどの効果はないので 8 ブロックのままにした
- **読み出しの上限**: SD と USB を順番に行う限り、1 ブロックあたり「SD 約 370µs + USB 約 670µs」で、約 490KB/s が上限。R5d（SPI 25MHz）で SD を縮めても 500KB/s 前後。これ以上速くするには、SD の読み出しと USB の送信を重ねる（SPI の DMA を非同期で使う）必要があり、14.3 節で「やらない」とした大きな変更になる
- FAT の走査（約 15,300 ブロック）は読み出しの速さに比例するので、今の速度では 14〜15 秒かかる。マウント後の遅さに対しては、カードをクラスタ 32KB の FAT32 にするほうがはるかに効く（14.2 節）

### 14.8 R5c の結果（2026-11-26）

実装: `Disk` に `max_write_blocks()` と `write_blocks()` を追加した（既定は 1 ブロックずつで、フロッピーは今までどおり）。`ReaderDisk` は最大 8 ブロックを 1 回のマルチブロック書き込み（embedded-sdmmc が ACMD23 で事前消去を指定してから CMD25）で書く。`usb::transfer` は最大 8 ブロックを USB から受け取ってからまとめて書く。ホストが途中で送るのをやめたときは、届いた分の完全なブロックだけを書く（今までと同じ）。コマンドをまたいでは溜めない。

| 設定 | 操作 | 書いたブロック | SD / ブロック | USB / ブロック | データフェーズの速度 | PC 側の時間 |
|------|------|--------------|--------------|---------------|--------------------|------------|
| R5a（1 ブロックずつ） | 5.9MB の書き込み + `sync` | 11,951 | 3,242µs | 919µs | 120KB/s | 53.6 秒 |
| **R5c（8 ブロックずつ）** | 5.9MB の書き込み + `sync` | 11,949 | **630µs** | 1,006µs | **305KB/s** | **23.5 秒** |
| R5c | フロッピーモード: 空イメージに小さいファイル 40 個 + `sync` | 838 | 2,568µs | 1,413µs | 125KB/s | 7.4 秒 |

確認したこと:

- リーダーモード: 再マウント後、R5c で書いた `_RDTEST3` と、R5a のときに書いた `_RDTEST2` の両方で、42 ファイルの SHA-256 がすべて一致した
- フロッピーモード: `newimg` で作った空イメージ（`NEW001.IMG`）を挿入して書き込み、再マウント後に 40 ファイルの SHA-256 がすべて一致した（書き込みの流れを作り直したため。フロッピーは今までどおり 1 ブロックずつ）
- 書き込みは 2.5 倍になり、14.5 節の目安（2 倍以上）を満たした

分かったこと:

- SD は 1 ブロック 3.2ms → 0.63ms に縮み、今は USB（1 ブロック約 1ms、64 バイトのパケット 1 個あたり約 126µs）のほうが長い。読み出しと同じく、USB はパケット 1 個ずつの受け取りが律速で、これ以上は SD と USB を重ねないと速くならない
- フロッピーモードの書き込みは 1 ブロックずつのまま（125KB/s）。フロッピーにもマルチブロックを使えば速くなるはずだが、フロッピーの用途では今の速度で困っていないので、入れるなら別の作業にする（PLAN.md の Phase 8）

計測の後始末: カードに `_RDTEST2`・`_RDTEST3`（リーダーモードのテスト用フォルダ）と `Floppy/NEW001.IMG`（フロッピーのテスト用イメージ）が残っている。安全チェックのため、削除は手作業で行う。挿入中のイメージは元の `vibeos.img` に戻した
